# 公测前置功能清单

> 状态：规划待启动。比赛期间（10~11 月）不实施，赛后按本文档排期启动。
> 日期：2026-10-10
> 关联：`design/match/2026-10-10-jinniu-competition-plan.md` §7（合规整改）、`design/feature_roadmap_brainstorm.md` §3.8

## 背景

当前线上为「访问码闸门 + 匿名 `clientId`」的单用户模式（`server/auth/access.ts`），满足邀请制内测需求。对外开放（公测）前必须补齐以下四组功能：

- **F1 / F2** 是账号与数据安全——公测上线的工程门槛
- **F3 / F4** 是生成式 AI 服务登记的前置要求——合规门槛

公测开放条件 = F1~F4 全部完成 **且** 生成式 AI 服务登记通过。

---

## F1 用户账号体系（自建，不走微信登录）

**驱动**：匿名 `clientId` 存 localStorage，换浏览器/清缓存即丢失全部衣橱与画像（留存杀手）；也是订阅收费与托管模式推送的前置依赖。

**范围**：
- 登录方式：**用户名 + 密码**，不验证邮箱/手机号（2026-10-10 决策：注册摩擦最小化，砍掉发信通道）
  - 找回通道：个人安全中心设置**密保问题**（2~3 个），重置密码需全部答对；答案哈希存储、输入归一化（去空格/大小写）、错误次数锁定
  - 可选增强：注册时发放一组**一次性恢复码**（用户自行保存），兜住密保答案遗忘的场景
  - 密码存储：Node 内置 `crypto.scrypt` + 每用户随机盐（零新依赖）
  - 已知代价与缓解：
    - 无验证联系方式 → 托管推送失去出站通道：用浏览器 Web Push（Push API，无需联系方式）+ 未来小程序订阅消息补
    - 密保答案遗忘率高于邮箱找回 → 多问题 + 恢复码 + 内测期人工兜底
    - 无实名锚点 → 生成式 AI 登记时可能被要求补实名机制，届时以手机号验证码升级（企业资质就绪后实施，保留升级口子）
- 登录态：复用并扩展 `server/auth/access.ts` 的 HMAC cookie 模式，签发用户级 session token（含 userId、过期时间），httpOnly + Secure，30 天滚动过期——不引入 Auth.js 等新依赖
- 数据模型：新增 `User` 表（id、username 唯一、passwordHash、密保问题与答案哈希、恢复码哈希）；`ClientProfile` / `Conversation` / `ClothingItem` 归属迁移到 `userId`
- 匿名数据迁移：首次登录后将 localStorage `clientId` 名下数据认领/合并到 `userId`（要求幂等、可重试）
- 安全基线：登录连续 5 次失败锁定、密保重置限频、密码最低强度 8 位
- 反机器人（图形/行为验证码）：内测期由访问码闸门承担，公测前评估补 Turnstile 等

**验收标准（草案）**：
- [ ] 用户名 + 密码注册/登录后生成 `userId`，旧 `clientId` 数据完整迁移（衣橱件数、画像、会话数一致）
- [ ] 同一账号跨设备登录看到同一衣橱
- [ ] 未登录调用核心写接口返回 401
- [ ] 密保重置：答对全部问题可重设密码；连续 5 次答错锁定
- [ ] 登录连续 5 次失败锁定
- [ ] 单测：scrypt 哈希/校验、session token 签发/校验、数据迁移幂等

## F2 服务端鉴权与资源归属校验

**驱动**：`clientId` 无校验，任何人拿到他人 `clientId` 即可读写其衣橱/会话（横向越权）；且 `isPublicReadRequest` 对衣橱、会话等接口裸放行 GET（`server/auth/access.ts`）。

**范围**：
- 所有 `/api/wardrobe`、`/api/conversations`、`/api/clients` 接口校验会话身份 + 资源归属（`userId === resource.ownerId`）
- 移除/收敛裸 GET 放行策略
- 访问码闸门保留为「内测模式」开关，公测时关闭

**验收标准（草案）**：
- [ ] 单测：携带用户 A 身份请求用户 B 的资源 → 403
- [ ] e2e：未登录 `GET /api/wardrobe` → 401
- [ ] 现有访问码路径在内测模式下不受影响（回归）

## F3 AI 生成内容标识

**驱动**：《人工智能生成合成内容标识办法》（2025-09-01 起施行），生成式 AI 服务登记材料项。

**范围**：
- 显式标识：效果图角落加「AI 生成」角标，分享/下载场景同样携带
- 隐式标识：图片元数据写入生成信息（产品名、生成时间、模型标识）
- 文案场景：对话 UI 固定展示「内容由 AI 生成」提示

**验收标准（草案）**：
- [ ] 新生成效果图均携带角标 + 元数据双标识（旧图不追溯）
- [ ] 下载/分享图片标识不被剥离

---

## F4 投诉举报与内容安全机制

**驱动**：《生成式人工智能服务管理暂行办法》要求提供投诉举报入口；登记材料中的「内容安全管理制度」需要落地载体。现状：server 侧无任何内容安全层，完全依赖模型提供方能力。

**范围**：
- 对话消息与效果图提供「举报」入口，落库并可查询
- 输入侧内容安全：评估是否补敏感词/输入过滤层（底线方案 = 依赖 DeepSeek/豆包自带安全能力 + prompt 拒答策略）
- 内容安全管理制度文档（安全评估报告附件，非代码）

**验收标准（草案）**：
- [ ] 举报提交后可在管理端/日志查询
- [ ] 明显违规输入触发拒答（补充进 `tests/prompts/` 回归测试）

## 排期建议

| 阶段 | 动作 |
|---|---|
| 比赛期间（10~11 月） | 全部不启动；访问码内测模式继续，评委凭码体验 |
| 赛后第一批 | **F3 + F4**（登记材料依赖，完成后即可提交登记，周期 1~3 个月） |
| 赛后第二批 | **F1 + F2**（强耦合，必须一起做：先账号再鉴权） |
| 公测开放 | F1~F4 完成 + 登记通过 |

> 注：托管模式「穿搭计划」属产品迭代（BP 主线），不在本清单；无邮箱/手机号的账号体系下，推送通道走浏览器 Web Push，后续微信小程序端用订阅消息 + 账号绑定，均不构成本清单的阻塞项。

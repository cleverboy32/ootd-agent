# 功能路线图 Brainstorm — 下一步可以做什么

> 状态：讨论中，未定稿。记录一次功能头脑风暴的结论，供后续挑选方向后再写正式的需求方案（含验收标准）。
> 日期：2026-07-07

## 1. 背景

已完成 Profile 中心、搭配质量优化（RAG 匹配质量、Gatekeeper/Stylist 意图裁决）等迭代后，讨论下一步该给这个应用加什么功能，才能让用户觉得"好用/离不开"。

先做了一次现状盘点，避免推荐重复造轮子。

## 2. 现状盘点摘要

**已实现：**
- 多轮 AI 穿搭对话（8 种意图路由、天气感知、颜色匹配、风格建议 `style_advice`）
- 衣橱管理：批量上传 + AI 自动分类打标 + 语义检索（RAG）+ 单删/批量删
- 搭配效果图生成 + 异步质检（Visual Critic）
- 用户档案：对话自动积累基础信息 + 自拍外形分析
- 工程：对话摘要压缩、断点续传、audit 日志、单测/Prompt 回归测/Playwright e2e

**明显空白（代码库里完全没有痕迹）：**
- 用户账号体系（现在是匿名 `clientId` 存 localStorage）
- 收藏 / 心愿单 / 已保存搭配方案（方案只存在于 `Message.content`，用完即丢）
- 穿搭日历 / OOTD 打卡记录
- 电商闭环（价格、品牌、购买链接、比价、购物车）
- 分享 / 社区 / 点赞
- 推送通知
- 数据统计（穿着频率、衣橱利用率）
- 衣橱单品编辑（现在只有增/查/删，没有改）
- 国际化

## 3. 功能建议（按投入分档）

### 第一档：低成本高价值，直接复用现有基建

**3.1 「我的搭配」收藏 / 方案库**
- 问题：Stylist 生成的结构化 outfit（单品 id + 效果图）只活在 `Message.content` 里，聊完就没了，用户没法回顾/复用满意的方案。
- 方案雏形：新增 `SavedOutfit` 表（关联 clientId、outfit 结构、效果图 URL、来源 messageId），聊天气泡里加"收藏"按钮，衣橱页或新增"我的搭配"页展示收藏列表。
- 价值：把一次性问答变成可复用资产，是收藏/日历/统计类功能的基础设施。

**3.2 衣橱单品编辑**
- 问题：AI 自动打标签偶尔出错（颜色/分类判断不准），用户无法自行纠正，只能删了重传；错标签会持续污染 RAG 检索结果。
- 方案雏形：`PATCH /api/wardrobe/[itemId]`，衣橱详情/网格加编辑入口（改分类、颜色、标签、描述）。
- 价值：修信任缺口，同时直接提升下游检索质量。

**3.3 衣橱利用率报告 / "吃灰单品"提醒**
- 前提：依赖 3.1（需要记录"哪些单品被选中过"）或至少记录 confirmed 方案里出现的 wardrobeId。
- 方案雏形：统计每件单品被选中的次数/最近一次时间，衣橱页展示"N 个月未被搭配"标记；`ragMatchQuality.ts` 里已有的槽位匹配质量评估可以复用于"衣橱缺口"分析。
- 价值：数据基本是现成的（`wardrobe_match_summary` + 方案选中 id），缺的只是记录表和统计页。

### 第二档：中等投入，强化日常打开习惯

**3.4 OOTD 打卡日历**
- 与 3.1 天然配对：收藏是"AI 建议的我喜欢"，打卡是"我今天实际穿的"。
- 价值：形成使用习惯，且实际穿着数据能反哺个性化推荐。

**3.5 分享卡片**
- 已有效果图生成能力，加一层"生成分享海报"（搭配图 + 简短文案 + 小 logo）即可，不需要做完整社区/点赞体系。
- 价值：低成本获客杠杆。

**3.6 每日天气主动推送**
- 天气服务（`amapWeatherService.ts`）已就绪，现在是被动等用户来问。
- 价值：从"需要时才想起"变成"每天习惯性打开"，但需要引入推送通道（当前依赖里没有）。

### 第三档：长线差异化，投入大，需明确战略方向后再启动

**3.7 缺口导向的主动购物建议**
- `purchase_pairing` 现在是被动的（用户上传待购单品才触发）。若长期积累 RAG 缺口分析，可以主动种草，但涉及电商链路，投入明显更大。

**3.8 用户账号体系**
- 现在匿名 `clientId` 存 localStorage，换设备/清缓存即丢档案和衣橱。长期留存迟早要补，但改动面大（登录、数据迁移），建议排最后。

## 4. 初步建议

优先做 **3.1（收藏方案库）+ 3.2（衣橱编辑）**：架构风险几乎为零，直接补齐现有体验短板，做完能立刻感知到变化，且是 3.3/3.4 等后续功能的基础设施。

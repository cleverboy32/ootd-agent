# 用户登录体系需求文档（F1 + F2）

> 状态：已定稿，进入实施
> 日期：2026-10-10
> 关联：`design/features/2026-10-10-public-launch-prerequisites.md`（F1/F2）、`design/match/2026-10-10-jinniu-competition-plan.md` §7

## 1. 背景与目标

当前线上为「访问码闸门 + 固定单用户 clientId」：`proxy.ts` 校验访问码 cookie 后给所有 `/api/*` 请求注入 `x-client-id: OWNER_CLIENT_ID`，route handler 从该 header 取身份；前端 `getClientId()` 返回构建期常量。存在问题：

- 无法多人使用：所有访问者共享同一身份、同一衣橱
- `isPublicReadRequest` 对衣橱/会话 GET 裸放行，未验证访问码也可读数据
- 无个人账号、无找回机制，是公测与订阅收费的前置缺失

**目标**：自建用户名+密码账号体系（邀请码注册），复用 `server/auth/access.ts` 的 HMAC cookie 模式签发用户 session；`proxy.ts` 解析 session 注入真实用户身份；全部资源接口完成归属校验（F2）。比赛演示零影响（`AUTH_MODE` 双模式开关，默认保持 access）。

## 2. 范围 / 非目标

**范围**：注册（邀请码）、登录、登出、session 管理、修改密码、密保找回、恢复码找回、安全中心页、登录/注册/找回页、F2 接口鉴权与归属校验、既有数据一次性迁移绑定、e2e 认证接入。

**非目标**：F3 AI 内容标识、F4 举报与内容安全（登记材料线，独立任务）；邮箱/短信验证码（已决策不做）；一人一码邀请制；Web Push；公开注册（生成式 AI 登记完成前维持邀请码）。

## 3. 术语

| 术语 | 含义 |
|---|---|
| access 模式 | `AUTH_MODE=access`，现有行为：访问码闸门 + 固定 owner 身份（比赛演示用） |
| user 模式 | `AUTH_MODE=user`，登录体系：session 闸门 + 真实用户身份 |
| `ootd-access` | 访问码 cookie（现有，不变） |
| `ootd-session` | 用户 session cookie（新增） |

## 4. 用户流程

### 4.1 注册
1. `/login` → 注册 tab：用户名 + 密码 + 确认密码 + 邀请码
2. 成功 → 自动登录 → 跳首页；系统为新用户自动创建空 `ClientProfile`
3. 失败反馈：用户名已占用 / 邀请码错误 / 字段格式不符

### 4.2 登录
- 用户名 + 密码 → 成功跳回 `redirect` 参数指定的来源页（默认首页）
- 连续 5 次失败锁定 15 分钟，提示剩余时间

### 4.3 登出
- Profile 页入口 → 清 session cookie → 跳 `/login`

### 4.4 忘记密码（密保找回）
1. `/login` → 忘记密码 tab → 输用户名
2. 展示该用户已设置的密保问题（2~3 个）
3. 全部答对 + 输入新密码 → 重置成功并自动登录；该用户所有旧 session 失效（`sessionVersion` +1）
4. 未设置密保 → 引导使用恢复码；两者都无 → 联系管理员人工兜底

### 4.5 忘记密码（恢复码找回）
- 输入任一未使用恢复码 + 新密码 → 重置成功；该恢复码即时作废

### 4.6 安全中心（`/settings/security`，需登录）
- **修改密码**：旧密码 + 新密码 → 成功后当前会话续签，其他设备 session 全部失效
- **设置/更新密保**：2~3 组问答，答案不留明文
- **生成恢复码**：8 个，仅展示一次（弹层 + 复制 + 「我已保存」确认）；重新生成则旧码全部作废

### 4.7 未登录访问（user 模式）
- 任意 `/api/*`（除 `/api/auth/*`）返回 401 `{ code: 'UNAUTHENTICATED' }` → 前端跳 `/login?redirect=<来源页>`

## 5. 字段与安全规则

| 项 | 规则 |
|---|---|
| username | 3~20 位，`^[a-zA-Z0-9_-]+$`，存储统一转小写，全库唯一 |
| password | ≥8 位且同时含字母与数字；`crypto.scrypt` + 随机盐哈希存储（Node 内置，零新依赖），格式 `scrypt:N:r:p:salt:hash`（base64） |
| 邀请码 | `REGISTRATION_MODE=invite`（默认）时必填，与服务端 `ACCESS_CODE` 常量时间比较（复用 `isAccessCodeValid`） |
| 密保问题 | 2~3 组；问题 4~50 字，答案 1~50 字；答案归一化（trim + 全角转半角 + 转小写 + 连续空格归一）后 scrypt 哈希 |
| 恢复码 | 8 个，格式 `XXXX-XXXX-XXXX`（Crockford base32 字母表），仅存哈希；一次性，使用即删 |
| 登录锁定 | 连续 5 次失败锁定 15 分钟（`failedLoginAttempts` / `lockedUntil` 持久化到 User 表）；登录成功清零；找回密码共享同一计数与锁 |
| session payload | `v1.{userId}.{sessionVersion}.{expiresAt}` + HMAC-SHA256 签名（复用 access.ts 模式） |
| session cookie | `ootd-session`，httpOnly + Secure（生产）+ SameSite=Lax + path=/，30 天固定有效期；**用 Lax 不用 Strict**（微信/QQ 内点开链接的首次导航需要携带 cookie，Strict 会导致已登录用户被误判未登录） |
| session 吊销 | 改密码 / 重置密码 → `sessionVersion` +1，旧票据全部失效（无状态票据的唯一吊销手段） |

## 6. API 契约（全部 `/api/auth/*`，proxy 放行）

| # | 方法/路径 | 请求体 | 成功 | 主要错误 |
|---|---|---|---|---|
| 1 | POST `/api/auth/register` | `{username, password, inviteCode?}` | 200 `{user:{id,username}}` + Set-Cookie | 400 VALIDATION_ERROR / 403 INVITE_INVALID / 409 USERNAME_TAKEN |
| 2 | POST `/api/auth/login` | `{username, password}` | 200 `{user}` + Set-Cookie | 401 CREDENTIALS_INVALID / 423 ACCOUNT_LOCKED `{retryAfterSec}` |
| 3 | POST `/api/auth/logout` | — | 200，清 cookie | — |
| 4 | GET `/api/auth/session` | — | 200 `{authenticated, user?:{id,username,hasSecurityQuestions}}` | — |
| 5 | POST `/api/auth/change-password` | `{oldPassword, newPassword}`（登录态） | 200 + 续签 cookie | 403 OLD_PASSWORD_WRONG / 400 VALIDATION_ERROR |
| 6 | GET `/api/auth/security-questions?username=x` | — | 200 `{questions: string[]}`（仅问题文本，找回密码用） | 404 统一返回空数组（避免用户名枚举） |
| 7 | POST `/api/auth/security-questions` | `{questions:[{question,answer}]}`（登录态） | 200 | 400 VALIDATION_ERROR |
| 8 | POST `/api/auth/recovery-codes` | —（登录态） | 200 `{codes: string[]}`（仅此次返回明文） | — |
| 9 | POST `/api/auth/reset-password` | `{username, method:'questions'\|'recovery', answers?:string[], recoveryCode?:string, newPassword}` | 200 + Set-Cookie | 403 ANSWERS_MISMATCH / RECOVERY_INVALID / 423 ACCOUNT_LOCKED |

约定：错误响应统一 `{ error: string, code?: string }`；登录态接口 401 `{ code: 'UNAUTHENTICATED' }`。

## 7. DB 变更（Prisma，`pnpm db:migrate`）

```prisma
model User {
  id                  String       @id @default(cuid())
  username            String       @unique              // 存小写
  passwordHash        String                            // scrypt:N:r:p:salt:hash (base64)
  securityQuestions   Json         @default("[]")       // [{question, answerHash}]
  recoveryCodeHashes  String[]     @default([])
  failedLoginAttempts Int          @default(0)
  lockedUntil         DateTime?
  sessionVersion      Int          @default(0)
  clientProfileId     String       @unique
  clientProfile       ClientProfile @relation(fields: [clientProfileId], references: [id])
  createdAt           DateTime     @default(now())
  updatedAt           DateTime     @updatedAt
}
```

`ClientProfile` 增加反向关系 `user User?`。纯新增表 + 列，无存量数据破坏。

## 8. proxy.ts 改造

`AUTH_MODE` 环境变量：`access`（默认，现状）/ `user`。

**user 模式**：
1. 放行 `/api/auth/*` 与 `/api/access/*`
2. 读 `ootd-session` cookie → 验 HMAC 签名 + 有效期 → 解析 `userId` / `sessionVersion`
3. Prisma 查 User（已确认：Proxy 在 Next 16 默认 **Node.js 运行时**，DB 直连可用）→ 用户不存在或 `sessionVersion` 不匹配 → 401
4. 注入 `x-client-id = user.clientProfileId`、`x-user-id = user.id`（**覆写客户端自报 header**，防伪造）
5. 无 session / 无效 → 401 `{code:'UNAUTHENTICATED'}`；`isPublicReadRequest` 在 user 模式停用（F2 移除裸放行）

**access 模式**：行为与现状完全一致（回归保障：`tests/unit/auth/access.test.ts` 不改动）。

已知取舍：实测每请求 User 查询 +200ms~1.2s（neon HTTP），已加进程内 30s TTL 缓存（`server/auth/sessionIdentityCache.ts`），命中后 proxy 耗时 4~6ms。吊销语义靠 sessionVersion 单调递增保持：新 token 首次请求即刷新缓存、旧 token 随即被拒；最坏情况（新 token 未发请求）旧 session 多存活一个 TTL。`bind-owner` 改 `clientProfileId` 后同样最多 30s 生效。

## 9. F2 归属校验

路由审计结论（2026-10-10，实施前核对）：**资源路由的归属逻辑已就位，无需新增 helper 抽象**——

- `messages` GET 按 `conversation.clientId` 过滤、POST 先查归属 → 404
- `wardrobe/[itemId]` GET 校验 `clientProfileId !== clientId` → 404；DELETE 经 service 按 clientId 过滤
- `conversations/[conversationId]` DELETE 校验归属 → 404
- `clients/[clientId]` 忽略路径参数，仅按注入的 header 身份操作
- 列表/创建路由按 clientId 过滤，天然隔离

因此 F2 的真正缺口是**身份可信性**，由两处闭环：
1. user 模式 proxy 从 session 解析身份并**覆写** `x-client-id`（客户端自报无效）
2. user 模式停用 `isPublicReadRequest` 裸放行，无 session 一律 401

access 模式下 proxy 强制注入 owner id，行为与现状一致。

## 10. 数据迁移（一次性脚本）

`scripts/bind-owner-profile.ts --user <username>`：
1. 查 User、查 `ClientProfile(id=OWNER_CLIENT_ID)`，任一缺失即报错退出
2. 校验该用户注册时自动建的 profile 为空（无 conversations / clothingItems），非空则停手（`--force` 可覆盖）
3. 事务：`User.clientProfileId` → 既有 profile；删除自动创建的空 profile
4. 幂等，可重复执行；输出迁移报告（绑定关系、清理行数）

执行时机：代码部署后、切 `AUTH_MODE=user` 之前。评委等新用户不受影响（各自空衣橱）。

## 15. 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| proxy 每请求查 User 表 | 实测每请求 +200ms~1.2s | 已加 30s TTL 身份缓存，命中 4~6ms；多实例部署时各进程独立缓存，吊销上限仍为一个 TTL |
| e2e 现有用例依赖访问码 | 阶段 5 批量失败 | 实施时先核对 setup，统一接入认证态 |
| 密保问题可被社工 | 账号被重置 | 内测规模可接受；恢复码优先引导；登记时按监管反馈再评估 |
| 忘记密码且无密保无恢复码 | 账号不可找回 | 注册与安全中心引导设置；管理员人工兜底 |
